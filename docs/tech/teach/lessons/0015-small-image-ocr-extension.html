Lesson 15 · 扩展案例

小图 OCR：从 Layout 盲区到专用 API

这节课只做一件事：当整页流水线对极小图片返回空结果时，能判断根因、绕开版面模型直接调用 OCR 原子模型，并把它封装成一个有边界、可部署的专用 API。

为什么学这个：这是“扩展 fork”的典型形态：不修改主流水线，而是在正确的层级增加一条受控旁路。课程 08 给的是清单，本课是一次完整演练。

你将能够

  • 区分“版面模型没看见”和“OCR 识别错”两类问题。
  • 用 AtomModelSingleton 按当前后端/设备直接调用 OCR，而不是绕过运行时。
  • 解释为什么小图会被整页 Layout 处理漏掉，以及哪些过滤规则会放大问题。
  • 实现一个带鉴权、大小限制、并发边界与错误映射的专用 OCR 端点。
  • 判断该端点应放在独立服务、file-parse、doclib 还是 api-server。

1. 现象：210×18 的图片，整页解析返回空

# 典型复现
from mineru.parser import parse

result = parse("crop_210x18.png", tier="standard", ocr_mode="ocr")
print(len(result.pages), result.structured_content())
# → 1 页，但没有任何文本块
  • 图片本身清晰、文字可读，直接看像素没有问题。
  • 换成更大的截图或把图放大 3 倍后重新解析，往往能出结果。
  • 同一个 API 对整页扫描件工作正常，只有极小输入失败。

2. 根因：整页 Layout 与小图的分辨率矛盾

输入图片转成 PDF 页面（页面尺寸≈图片尺寸）
页面级 Layout整页缩放到模型输入尺寸
小区域信息不足检测框过小/置信度低 → 被过滤
后续阶段无事可做没有块 → 没有 OCR → 空结果
# model/layout/pp_doclayout_v2_base.py —— 小框会被显式过滤
x1, y1, x2, y2 = box["bbox"]
width = float(x2) - float(x1)
height = float(y2) - float(y1)
if (width < 6.0 or height < 6.0) and (drop_inline_formula or not cls._is_inline_formula_box(box)):
    dropped_indexes.add(i)
  • Layout 是页面级模型：它先看整页，再给出块。极小页面/极小区域在缩放后只剩几个像素，检测不到是设计取舍，不是“识别模型坏了”。
  • 过滤规则会再丢掉宽或高小于 6 的框；对本身就只有十几像素高的裁剪图，余量非常小。
  • 图片转 PDF 后没有原生文本层，txt 路径无从取证，只能依赖 OCR；而 OCR 又依赖 Layout 先给出块。
  • 解决办法不是调大阈值（会影响正常页面），而是在需要时绕开 Layout，直接 OCR。

4. 直调 OCR 原子模型

不要直接 PytorchPaddleOCR() 或手拼 ONNX 路径；使用 AtomModelSingleton，它会按当前配置选择 ONNX/Torch、设备、语言和权重缓存。

# tools/direct_ocr.py —— 最小直调示例（Python 3.11+）
from mineru.model.runtime.contracts import AtomicModelName
from mineru.model.runtime.hybrid import AtomModelSingleton


def get_ocr_engine(lang: str = "ch"):
    """按运行时配置获取共享 OCR 引擎；首次调用才加载权重。"""
    return AtomModelSingleton().get_atom_model(
        atom_model_name=AtomicModelName.OCR,
        small_backend=None,          # None → resolve_small_model_backend()
        device=None,                 # None → ONNX CPU / Torch get_device()
        lang=lang,                   # "ch" 普通文字；"seal" 印章
        det_db_box_thresh=0.5,
        det_db_unclip_ratio=1.5,
        enable_merge_det_boxes=True,
    )


def ocr_image_bytes(data: bytes, lang: str = "ch") -> list[dict]:
    engine = get_ocr_engine(lang)
    batch = engine.ocr(data)         # bytes 由 check_img 解码为 BGR ndarray
    lines: list[dict] = []
    for page_res in batch or []:
        for box, (text, score) in page_res or []:
            lines.append({"box": box, "text": text, "score": float(score)})
    return lines
返回约定：ocr() 返回按输入顺序的列表；每页是 [[四个点坐标], (text, score)] 的列表，或 None。坐标是输入图像像素，不是 0–1000，也不是页面坐标。
配置效果
lang="ch"普通文字；字符表 PP-OCRv6
lang="seal"印章模式；多边形检测、专用裁剪与阈值
small_backend="onnx"CPU、DirectML/WebGPU 等 ONNX 路径
small_backend="torch"CUDA/MPS/XPU 等 Torch 路径
enable_merge_det_boxes合并相邻检测框；小图可先保持默认，再按样本调整

5. 封装成专用 API

推荐先做独立小服务：它不改变 Tasks/Doclib 契约，失败也不会影响主解析。等它稳定并成为产品能力，再提升为 kit 路由。

# tools/image_ocr_service.py —— 独立 FastAPI 服务骨架
from __future__ import annotations

import asyncio
import threading

from fastapi import FastAPI, File, Header, HTTPException, UploadFile
from fastapi.responses import JSONResponse

MAX_BYTES = 8 * 1024 * 1024
API_KEY = ""                           # 生产从环境变量读取
app = FastAPI(title="MinerU image OCR")

_engine = None
_engine_lock = threading.Lock()
_infer_lock = threading.Lock()


def _get_engine():
    """惰性加载：import 不触发重依赖，首次请求才初始化模型。"""
    global _engine
    if _engine is None:
        with _engine_lock:
            if _engine is None:
                from mineru.model.runtime.contracts import AtomicModelName
                from mineru.model.runtime.hybrid import AtomModelSingleton

                _engine = AtomModelSingleton().get_atom_model(
                    atom_model_name=AtomicModelName.OCR,
                    lang="ch",
                    det_db_box_thresh=0.5,
                    det_db_unclip_ratio=1.5,
                    enable_merge_det_boxes=True,
                )
    return _engine


@app.get("/health")
async def health() -> dict:
    return {"status": "ok"}


@app.post("/v1/image-ocr")
async def image_ocr(
    file: UploadFile = File(...),
    authorization: str | None = Header(default=None),
) -> JSONResponse:
    if API_KEY and authorization != f"Bearer {API_KEY}":
        raise HTTPException(status_code=401, detail="invalid_api_key")

    data = await file.read()
    if not data:
        raise HTTPException(status_code=400, detail="empty_file")
    if len(data) > MAX_BYTES:
        raise HTTPException(status_code=413, detail="file_too_large")

    def run():
        engine = _get_engine()
        with _infer_lock:                      # 共享本地模型对象串行推理
            return engine.ocr(data)

    try:
        batch = await asyncio.to_thread(run)
    except Exception as exc:
        return JSONResponse(status_code=503, content={"error": {"code": "ocr_failed", "message": str(exc)}})

    lines = []
    for page_res in batch or []:
        for box, (text, score) in page_res or []:
            lines.append({"box": box, "text": text, "score": float(score)})
    return JSONResponse(content={"lines": lines, "count": len(lines)})

uvicorn tools.image_ocr_service:app --host 127.0.0.1 --port 8010
curl -X POST http://127.0.0.1:8010/v1/image-ocr \
  -H "Authorization: Bearer $OCR_API_KEY" \
  -F "file=@crop_210x18.png"
落点适合代价
独立 FastAPI 服务专用旁路、快速验证、与主服务隔离多一个部署单元与鉴权面
mineru/kit/file_parse已有单文件同步包装、需要复用其上传/恢复要遵循其请求/记录生命周期
mineru/doclib 服务路由需要入库、缓存、locator、权限引入状态与迁移成本
api-server要成为正式产品能力、进入 Tasks 契约需要协议、错误码、测试全套

6. 护栏：旁路也必须守规矩

#检查做法
1导入无副作用重依赖在函数内导入；模块只定义 app 与常量
2走统一运行时用 AtomModelSingleton，不手拼权重路径
3资源边界大小上限、像素上限、并发信号量、超时
4安全默认 loopback；API Key；不接受任意 URL
5隐私本地 OCR 不上传；若要远程，必须显式配置 VLM/服务地址
6可观测请求 ID、耗时、图片尺寸、命中行数；失败保留错误码

7. 何时不该用这条旁路

  • 整页文档仍应走主流水线：Layout 提供阅读顺序、表格/公式结构，直调 OCR 会丢掉这些语义。
  • 需要表格/公式：直调 OCR 只给文字行；表格结构和公式 LaTeX 属于 MFR/表格模型或 VLM。
  • 需要 locator/缓存：应该用 Doclib，而不是自己维护一套文件索引。
  • 输入是扫描页：优先用 standard 或 basic 的整页流水线，旁路只处理“页面级模型确实看不见”的极小输入。

9. 动手挑战

  1. 从一份发票上裁出 210×18 的字段图，分别用整页 parse(tier="standard", ocr_mode="ocr") 与直调 OCR，记录输出差异。
  2. 把直调脚本封装成上面的 FastAPI 服务，用 curl 调通；再加一个“空文件 / 超大文件 / 错误 Key”的测试。
  3. 把服务输出与整页解析结果对照：哪些字段直调更好，哪些必须依赖 Layout（阅读顺序、表格、公式）？写进 NOTES。
  4. 给端点加一个并发上限（信号量），用 10 个并发请求压测，观察延迟与内存。
