1. 回顾与导入

第 1 课中，我们运行了 mineru demo/pdfs --output-dir demo/output，成功把一个 PDF 转成了 Markdown。你可能会好奇：这个过程中 MinerU 内部发生了什么？为什么有不同的"引擎"选择？

本节课，我们将掀开 MinerU 的引擎盖，看看它的内部结构。

2. MinerU 宏观架构

从最高层看，MinerU 的处理流程是：

输入文档
  │
  ▼
┌─────────────────────────────────────────┐
│  1. 文件类型识别                         │
│     (PDF / 图片 / DOCX / PPTX / XLSX)   │
└──────────────────┬──────────────────────┘
                   ▼
┌─────────────────────────────────────────┐
│  2. Office 文档走独立解析路径            │
│     (DOCX/PPTX/XLSX → 原生解析)         │
│     非Office文档继续往下                  │
└──────────────────┬──────────────────────┘
                   ▼
┌─────────────────────────────────────────┐
│  3. 后端引擎解析 (本章重点)              │
│     pipeline  │  vlm-engine  │  hybrid  │
└──────────────────┬──────────────────────┘
                   ▼
┌─────────────────────────────────────────┐
│  4. 输出生成                             │
│     中间JSON → Markdown / JSON / 图片    │
└─────────────────────────────────────────┘

四层架构

MinerU 的代码组织也遵循这个流程，分为四层：

层级路径职责
CLI 层 mineru/cli/ 命令行解析、Gradio Web UI、FastAPI 服务、API 客户端、参数校验
调度层 mineru/cli/common.py 识别文档类型，根据 backend 参数分派到对应的引擎
引擎层 mineru/backend/ pipeline / vlm / hybrid / office 四大处理引擎
模型 & 数据层 mineru/model/ + mineru/data/ 布局分析、OCR、表格识别、公式识别；数据读写抽象

这四个层级从上到下，职责分明。作为使用者，你主要打交道的是一、二层（CLI 参数和引擎选择）。

3. 三大引擎深入对比

这是 MinerU 最核心的设计决策——三种不同的解析方式。我们逐一来看。

pipeline（流水线引擎）

这是 MinerU 最"传统"的引擎。它像一条工厂流水线，多个深度学习模型各司其职、顺序执行：

PDF/图片
  │
  ▼
┌──────────────┐
│  ① 文字检测  │  ← PP-OCRv6 (检测文字位置)
└──────┬───────┘
       ▼
┌──────────────┐
│  ② 文字识别  │  ← OCR 模型 (识别文字内容)
└──────┬───────┘
       ▼
┌──────────────┐
│  ③ 布局分析  │  ← 检测标题、表格、图片等区域
└──────┬───────┘
       ▼
┌──────────────┐
│  ④ 表格识别  │  ← 专门模型识别表格结构
└──────┬───────┘
       ▼
┌──────────────┐
│  ⑤ 公式识别  │  ← MFR 模型 (公式→LaTeX)
└──────┬───────┘
       ▼
    输出 Markdown

特点：

  • 每个步骤都由专门的模型处理
  • 资源占用极低，可以跑在纯 CPU 上
  • 启动快，适合批量处理
  • 在 OmniDocBench v1.5 上达到 86.2 分

对应源码：mineru/backend/pipeline/

vlm-engine（视觉语言模型引擎）

这是 MinerU 最"现代"的引擎。它使用一个多模态大模型（MinerU2.5-Pro），直接"看"文档并理解其内容：

PDF/图片
  │
  ▼
┌──────────────────────────────────────────┐
│  VLM（视觉语言模型）                       │
│  一个模型同时完成：                          │
│  · 布局分析  · 文字识别  · 表格识别  · 公式  │
└──────────────────┬───────────────────────┘
                   ▼
                输出 Markdown

特点：

  • 一个模型完成所有任务，上下文理解更准确
  • 精度最高，尤其擅长复杂排版
  • 需要 GPU，显存要求较高
  • 适合对精度要求极高的场景

对应源码：mineru/backend/vlm/

hybrid-engine（混合引擎） 默认推荐

这是 MinerU 的默认引擎，也是最具巧思的设计——它结合了前两者的优点：

PDF/图片
  │
  ├── 如果是文本型PDF → 直接提取文字
  │                        │
  │                        ▼
  ├── 如果是扫描型PDF → VLM 解析（走 vlm-engine 路径）
  │
  ▼
  VLM 辅助修正文字提取结果中的问题（公式、表格等）
  │
  ▼
 输出 Markdown

特点：

  • 文本型 PDF 走快速文字提取路径
  • 复杂内容再用 VLM 辅助修正
  • 速度和精度的最佳平衡
  • 两个 effort 参数：medium（快速）和 high（高精度）

对应源码：mineru/backend/hybrid/

4. 调度层：引擎是怎么被选中的？

我们来看一段真实的源码。打开 mineru/cli/common.py，核心调度逻辑在这个函数中（约第 680-760 行）：

def do_parse(... , backend="hybrid-engine", ...):
    # 第 1 步：识别并处理 Office 文档 (DOCX/PPTX/XLSX)
    need_remove_index = _process_office_doc(...)

    # 第 2 步：根据 backend 参数分发
    if backend == "pipeline":           → _process_pipeline(...)
    elif backend.startswith("vlm-"):   → _process_vlm(...)
    elif backend.startswith("hybrid-"): → _process_hybrid(...)

当你在命令行中指定 --backend pipeline 时，MinerU 就会调用对应的处理函数。这些函数在 mineru/backend/ 下各自独立实现。

💡 源码阅读技巧

现在你不需要看懂所有代码，但你可以用这个思路去理解任意开源项目：从入口文件开始，追踪关键函数调用。对于 MinerU，入口是 mineru/cli/client.py 中的 main()，它调用 common.py 中的 do_parse()，后者分派到 backend/ 下的具体引擎。

5. Office 解析：被独立处理的"特长生"

细心的你可能注意到了，在 common.py 的调度逻辑中，Office 文档 (DOCX/PPTX/XLSX) 是最先被处理的，而且是独立路径：

def do_parse(...):
    # Office 文档最先被处理并移除
    need_remove_index = _process_office_doc(output_dir, pdf_file_names, ...)
    for index in sorted(need_remove_index, reverse=True):
        del pdf_bytes_list[index]
        ...

    # 剩下的 PDF/图片才进入后端引擎
    if backend == "pipeline":  ...
    elif backend.startswith("vlm-"): ...
    elif backend.startswith("hybrid-"): ...

为什么？因为 Office 文档 本机就是结构化的——DOCX 本质是一个 ZIP 包里面的 XML 文件，段落、表格、图片信息都是现成的。不需要"解析"，只需要"读取"。所以 MinerU 直接用 python-docx、pypptx、openpyxl 等库来提取内容，速度快、精度高。

对应源码：mineru/backend/office/

6. 一个完整的解析流程

现在我们把所有环节串起来，看看一个 PDF 从输入到输出经历了什么：

① 你输入：mineru report.pdf --backend hybrid-engine

② CLI 层解析参数 → 走到 common.py 的 do_parse()

③ 检查是否是 Office 文档 → 不是（是 PDF）

④ 根据 backend=hybrid-engine → 调用 _process_hybrid()

⑤ hybrid 引擎判断 PDF 类型：
    ├── 文本PDF → pypdfium2 提取文字 + VLM 辅助修正
    └── 扫描PDF → VLM 进行完整的视觉解析

⑥ 引擎输出 → 中间 JSON 格式

⑦ 中间 JSON → 最终输出 Markdown / JSON / 图片

⑧ 你得到：report.md （可读、结构化的文档）

这个流程中，步骤 ⑤ 是最核心的部分——不同引擎在这里展现出截然不同的能力。

7. 决策树：我应该用哪个引擎？

面对一个具体的解析任务，你可以按下面的思路选择引擎：

你的文档是 Office 格式？(DOCX/PPTX/XLSX)
  ├── ✅ → 自动走 Office 原生解析，无需选择引擎
  └── ❌ → 是 PDF 或图片，问下一个问题

你的机器有 GPU 吗？
  ├── ❌ 没有 → 用 pipeline（CPU 也能跑）
  └── ✅ 有 → 问下一个问题

你对精度要求有多高？
  ├── 一般 → hybrid-engine medium（默认，最快）
  ├── 较高 → hybrid-engine high（精度更好）
  └── 极高（复杂排版/扫描件） → vlm-engine

对于绝大多数日常场景，hybrid-engine medium 是最佳起点。如果发现解析结果不理想，再尝试换成 high 或 vlm-engine。

8. 动手实践：对比三个引擎

我们来做一个小实验——用同一个 PDF 分别用三个引擎解析，比较结果差异。

用 hybrid-engine 解析（默认）

mineru demo/pdfs --output-dir demo/output_hybrid

用 pipeline 解析

mineru demo/pdfs --output-dir demo/output_pipeline --backend pipeline

用 vlm-engine 解析（有 GPU 时）

mineru demo/pdfs --output-dir demo/output_vlm --backend vlm-engine

对比输出

分别打开三个输出目录中的 Markdown 文件，比较：

  • 标题层级是否一致？
  • 表格是否都被正确识别了？
  • 公式是否都被转换为 LaTeX 了？
  • 哪个引擎的排版最接近原始 PDF？
⚠️ 注意

pipeline 引擎不需要 GPU，应该总会成功。vlm-engine 需要 GPU，如果你的机器没有 GPU，可以跳过这一步。hybrid-engine 也需要 GPU，但它的模型比 vlm-engine 轻量。

9. 小测验

问题 1： MinerU 处理 DOCX 文档时使用哪个引擎？

  1. pipeline
  2. vlm-engine
  3. hybrid-engine
  4. 以上都不对，走 Office 独立解析路径
查看答案

D。Office 文档（DOCX/PPTX/XLSX）有独立的解析路径，直接读取其内部结构化的 XML 数据，不经过三大引擎。

问题 2： hybrid-engine 的 effort=medium 和 effort=high 主要区别是什么？

  1. medium 用 OCR，high 用 VLM
  2. medium 更快但部分功能受限（如图像分析），high 精度更高
  3. medium 只支持英文，high 支持所有语言
  4. 无区别
查看答案

B。medium 速度更快（提升 35%~220%），精度略低（仅降 0.13 分），但 medium 不支持图像分析功能。high 提供完整的解析精度。

问题 3： 如果服务器只有 CPU，没有 GPU，应该用哪个引擎？

  1. pipeline
  2. vlm-engine
  3. hybrid-engine
  4. 以上都可以
查看答案

A。pipeline 是唯一支持纯 CPU 运行的引擎。vlm-engine 和 hybrid-engine 都需要 GPU。
