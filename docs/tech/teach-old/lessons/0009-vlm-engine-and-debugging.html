3. 关键节点逐个拆

3.1 client.py::run_orchestrated_cli：为什么 CLI 要起一个 API 服务

mineru/cli/client.py:1185 的 main() 只做一件事：

asyncio.run(run_orchestrated_cli(...))

真正的编排逻辑在 client.py:910 run_orchestrated_cli()，它的工作分三步：

  1. 起子进程：用 subprocess 拉起 mineru.cli.fast_api:main，监听一个随机本地端口（你日志里的 http://127.0.0.1:11175）。
  2. 健康检查 + 上传：轮询 /health，通过 /file-upload 把 PDF 字节传给子进程。
  3. 提交任务 + 轮询：调 /task-start 提交，然后轮询 /task-status，完成后下载结果到 -o 指定目录。

这样设计有两个好处：

  • 故障隔离：GPU 推理崩了不会拖垮 CLI 本身，子进程退出后下次 CLI 还能起新进程。
  • 天然水平扩展：--api-url 传一个远端服务地址，run_orchestrated_cli 就变成"客户端逻辑"，多台 GPU 机器各起一个服务就能负载均衡。
调试影响巨大

因为工作线程在子进程里，你在 common.py / hybrid_analyze.py 打的断点必须能命中子进程。VS Code 默认不会自动 attach 到 subprocess，要么在 launch.json 里 "subProcess" 项启用子进程调试，要么干脆直接调 fast_api.py 这个入口（见第 5 节）。

3.2 fast_api.py::run_parse_job：同步后端走同步，异步后端走异步

子进程里的 fast_api.py:822 run_parse_job() 收到任务后，分发只看一行：

# fast_api.py:863-866
if request_options.backend == "pipeline":
    await asyncio.to_thread(do_parse, **parse_kwargs)   # 同步版
else:
    await aio_do_parse(**parse_kwargs)                   # 异步版

这句话很关键——它告诉了我们三件事：

  1. pipeline 后端在 hybrid 的地盘里也走同步 do_parse，只是外面套了一层 asyncio.to_thread，避免阻塞事件循环。
  2. hybrid / vlm-engine 后端走 异步 aio_do_parse。
  3. 你今天选中 common.py:667 do_parse 这一行，之所以断点不会命中，是因为你 -b hybrid 时根本不会调 do_parse。

3.3 common.py::aio_do_parse：异步版调度中心

结构与第 8 课同步版几乎对称，只是多了一步 Office 文档处理必须扔到线程池：

# common.py:785-840（节选）
backend = normalize_backend(backend)
need_remove_index = await asyncio.to_thread(_process_office_doc, ...)
if backend == "pipeline":
    _process_pipeline(...)            # 暂不支持异步，直接同步
elif backend.startswith("vlm-"):
    ...
elif backend == "hybrid":
    await _async_process_hybrid(...) # ★ 你看到的路径

所以在 hybrid 链路里 aio_do_parse 的职责就是按 backend 选分支，自己几乎不做业务。真正的"打包多文档 + 切窗口"在下一步。

3.4 hybrid_analyze.py::aio_doc_analyze：为什么有两个 configured_window_size

看 hybrid_analyze.py:924 和 :1132，两处都在读 get_processing_window_size(default=64)。这是因为 hybrid 的并行设计了两个循环：

  • :924：处理"先做 pipeline 部分再交给 VLM"的串行循环（_do_predict_analyze 路径）。
  • :1132：异步批处理主入口（aio_doc_analyze）。

这正好是第 8 课场景 4 提到的"config_reader.py:158 get_processing_window_size()"被两处调用的原因。你改了默认值或设了环境变量，两条链路同时受影响。

3.5 vlc_analyze.py::_get_model_async：asyncio.to_thread 的妙用

这是整条链中最容易卡住、也最容易让初学者心头一紧的节点：

# vlm_analyze.py:265-277
async def _get_model_async(backend, model_path, server_url, **kwargs):
    return await asyncio.to_thread(
        ModelSingleton().get_model,
        backend, model_path, server_url, **kwargs,
    )

看起来只是把同步 get_model 包了一层，为什么这么做？因为 ModelSingleton.get_model 会：

  1. 导入 lmdeploy（包含 Triton / CUDA 相关 C++ 扩展）
  2. 加载 VLM 权重到显存（InternVL3 约 2–4 GB）
  3. 构建 VLAsyncEngine + 预热

整个过程是阻塞 CPU 的几十秒操作。如果直接在协程里调，FastAPI 的事件循环会整个冻住，/health 都响应不了。asyncio.to_thread 把它丢到默认线程池，事件循环可以继续接受别的请求。

断点命中现象

你在 vlc_analyze.py:199 get_model 里的断点能命中，但调用栈看起来很奇怪——它会"穿过"asyncio 和 concurrent.futures 的内部帧。这是正常的：因为协程把这个函数委派给了线程池执行，线程切换会让调试器的栈视图跳一下。继续单步即可，不要被栈视图异常吓到。

3.6 vlc/utils.py::set_lmdeploy_backend：CUDA 检查点

这是今天那条报错的发源地：

# vlm/utils.py:60-80
def set_lmdeploy_backend(device_type: str) -> str:
    if device_type.lower() in ["ascend", "maca", "camb"]:
        lmdeploy_backend = "pytorch"
    elif device_type.lower() in ["cuda"]:
        import torch
        if not torch.cuda.is_available():
            raise ValueError("CUDA is not available.")   # ★ 第 66 行
        if is_windows_environment():
            lmdeploy_backend = "turbomind"
        elif is_linux_environment():
            major, minor = torch.cuda.get_device_capability()
            compute_capability = f"{major}.{minor}"
            if version.parse(compute_capability) >= version.parse("8.0"):
                lmdeploy_backend = "pytorch"
            else:
                lmdeploy_backend = "turbomind"
        else:
            raise ValueError("Unsupported operating system.")
    else:
        raise ValueError(f"Unsupported lmdeploy device type: {device_type}")
    return lmdeploy_backend

三件事一眼看明白：

  1. 检查的不是"有 GPU"，而是torch.cuda.is_available()——装的是 CPU 版 PyTorch 就会失败，哪怕机器有 GPU。
  2. Windows 强制用 turbomind，Linux 会按 compute_capability >= 8.0 分给 pytorch 还是 turbomind。
  3. 不支持 macOS / 其他系统，会在第 77 行直接 raise。

记住：set_lmdeploy_backend 只选 backend，不做推理。选完才到 vlc_analyze.py:202-221 构造 PytorchEngineConfig 或 TurbomindEngineConfig，然后交给 VLAsyncEngine。

4.4 高频错误速查

错误 A：CUDA is not available

症结：torch.cuda.is_available() 返回 False。

排查命令：python -c "import torch; print(torch.__version__, torch.cuda.is_available())"

常见原因：① 安装的是 CPU 版 PyTorch（pip install torch 默认是 CPU 版）；② CUDA 驱动没装或版本低于 PyTorch 要求；③ 在 WSL 里但 CUDA 没透传。

修法：重装 CUDA 版：pip install torch --index-url https://download.pytorch.org/whl/cu121（按显卡选 cu118/cu121/cu124）。

错误 B：ModuleNotFoundError: lmdeploy

症结：vlc_analyze.py:199 里 import lmdeploy 抛错。

常见原因：MinerU 用 extras 安装，没装 VLM 依赖；或 conda 环境没切对。

修法：pip install "mineru[vlm]" 或 pip install lmdeploy。Windows 用户注意 lmdeploy 对 Windows 支持差，建议用 WSL 或换 pipeline 后端。

错误 C：断点不命中

症结：红点点了半天，F5 启动后就是不停。

排查：① launch.json 里 justMyCode 是不是 false？② subProcess 是不是 true？③ 是不是在 common.py:668 do_parse 打断点，但实际跑的后端是 hybrid（命中点在 aio_do_parse）？

错误 D：环境变量没生效

症结：export MINERU_PROCESSING_WINDOW_SIZE=8 后，日志里 window_size 还是 64。

排查：① launch.json 的 env 块有没有写？② 如果用 PowerShell，set 是会话级的，export 在 PowerShell 不生效，要用 $env:MINERU_PROCESSING_WINDOW_SIZE=16。③ 子进程的环境变量是从父进程继承的，重启 IDE 再试。

5. lmdeploy 速览（够用就好）

lmdeploy 是上海 AI 实验室开源的 LLM/VLM 推理框架，MinerU 默认 VLM 模型用的是自家的 InternVL 系列。set_lmdeploy_backend 选的也不是"用不用 lmdeploy"，而是"用 lmdeploy 的哪条后端"：

后端平台特点
turbomindLinux + Windows自研 C++ 引擎，基于 Triton，PagedAttention + Continuous Batching，性能最佳
pytorchLinux用 PyTorch 原生 SDPA/FlashAttention，支持更广模型，兼容 8.0+ 算力
远端服务任意把 lmdeploy 起成独立 HTTP 服务，MinerU 通过 --server-url 调用，避免本机 CUDA 依赖

对调试来说只要记三件事：

  1. MinerU 不强依赖 lmdeploy，可以 pip install "mineru[core]" 只装 pipeline；VLM 才需要额外装 lmdeploy。
  2. 你今天踩的坑不是 lmdeploy 本体的问题，是 lmdeploy 在 选 backend 时做了 CUDA 探测。
  3. 如果不想在本机跑 lmdeploy，可以部署一个远端服务，MinerU 这边的 server_url 参数就是干这个的（看 vlc_analyze.py:267 _get_model_async 的签名里有 server_url: str | None）。

6. 绕开 VLM 的两条退路

有时候你只是想让流程跑通（比如在没 GPU 的笔记本上调试），没功夫折腾 CUDA。两条退路都能完成任务：

退路 A：换 -b pipeline 后端

改哪里：launch.json 的 args 把 "-b", "hybrid" 改成 "-b", "pipeline"。

效果：在 fast_api.py:863 那个判断直接走 do_parse，再也不会碰到 set_lmdeploy_backend。你打开 vlc/utils.py:66 的断点完全不会命中——因为整条 VLM 分支被跳过了。

代价：没有 VLM 做复杂版面兜底，对公式密集或图文混排的 PDF 效果会差一些。但调试 pipeline 本身、调试 asyncio 时序、调试 CLI 参数足够了。

退路 B：远端 lmdeploy 服务 + --server-url

做法：在一台有 GPU 的机器上 lmdeploy serve api_server OpenGV/InternVL3-1B --port 23333，然后在 MinerU 客户端这边传 server_url="http://gpu-host:23333"。

效果：vlc_analyze.py:199 get_model 走到 MinerUClient(server_url=...) 分支，本机不再需要 GPU / lmdeploy / torch CUDA 版。

适用场景：团队有一台 GPU 服务器，开发者本地调试客户端逻辑。

组合用法

调试时用退路 A（快、简、稳），功能验证时切回 hybrid 。两条退路都不改源码，只改 launch.json 或环境变量——这是第 3 课"环境变量优先于代码修改"原则的延续。

7. 小测验

问题 1： 你在 mineru/cli/common.py:668 do_parse 行打断点，启动 mineru -p demo.pdf -b hybrid，断点不会命中。原因是？

  1. justMyCode 没改成 false
  2. do_parse 是同步版，hybrid 后端走 aio_do_parse
  3. 断点在子进程，没启用 subProcess: true
  4. Python 缓存了旧字节码
查看答案

B。fast_api.py:863-866 的分发只会在 backend == "pipeline" 时调 do_parse；hybrid / vlm-* 都走 aio_do_parse（common.py:766）。A/C/D 都会让你断不到任何地方，不止这一行；只有 B 是"你能断到别的，就是断不到 668"的真正原因。

问题 2： vlc_analyze.py:271 的 asyncio.to_thread 为什么要这么写？

  1. 绕过 GIL 限制
  2. 把模型加载这种 CPU 阻塞操作丢到线程池，避免 FastAPI 事件循环卡死
  3. 用多进程提升推理速度
  4. lmdeploy API 规定必须这么用
查看答案

B。ModelSingleton.get_model 会导入 lmdeploy + 加载权重 + 预热，几十秒阻塞。直接在协程里调会冻住整个事件循环，/health 都不响应。asyncio.to_thread 不是为了多进程（它用的是线程池），也不是为了绕 GIL（模型加载本身就慢），纯粹是把阻塞操作隔离出协程。

问题 3： 报错 ValueError: CUDA is not available. 来自哪一行？

  1. vlc_analyze.py:199 get_model
  2. vlc/utils.py:66 set_lmdeploy_backend
  3. hybrid_analyze.py:1116 aio_doc_analyze
  4. fast_api.py:822 run_parse_job
查看答案

B。堆栈最底下一帧就是真正抛错的位置。这里就是 set_lmdeploy_backend 第 66 行的 raise。A/C/D 都是上游调用链的一环，能看到异常冒泡，但不是源头。
