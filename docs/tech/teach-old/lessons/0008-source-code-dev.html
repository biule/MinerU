2. 调用链追踪：一个命令走多远

在终端输入 mineru -p demo.pdf -o output 后，代码走了多远？我们一步步追踪：

client.py
main() → common.py
do_parse() → pipeline_analyze.py
doc_analyze_streaming() → model_init.py
AtomModelSingleton → pipeline_middle_json
union_make() → data_reader_writer.py
FileBasedDataWriter

这六个节点构成了 MinerU 的"主干道"。下面逐一拆解每段代码做了什么。

第 1 站：client.py → main()

pyproject.toml 中定义了入口：

[project.scripts]
mineru = "mineru.cli.client:main"

这里的 main() 是 Click 装饰的函数（约 1000+ 行），负责解析所有 CLI 参数，然后调用 common.py。当你运行 mineru -p ... 时，Click 框架自动把 -p 映射到 path 参数，--backend 映射到 backend 参数，以此类推。

第 2 站：common.py → do_parse()

这是 MinerU 的调度中心（约 700 行），逻辑流程：

def do_parse(..., backend="hybrid-engine", ...):
    # 1. 识别并处理 Office 文档（DOCX/PPTX/XLSX）
    need_remove = _process_office_doc(...)
    # 2. 剩下的 PDF/图片根据 backend 参数分派
    if backend == "pipeline":
        _process_pipeline(...)    # → pipeline_analyze.py
    elif backend.startswith("hybrid-"):
        _process_hybrid(...)      # → hybrid_analyze.py
    elif backend.startswith("vlm-"):
        _process_vlm(...)         # → vlm_analyze.py

这就是第 2 课讲的"调度层"——判断文档类型，选择引擎路径。

第 3 站：pipeline_analyze.py → doc_analyze_streaming()

我们在第 6 课的 Python API 中直接调用的就是它。内部逻辑是"处理窗口"机制——把多页 PDF 分批次交给模型推理，batch 之间可以释放显存。

第 4 站：model_init.py → AtomModelSingleton

单例模式——全局只有一个模型实例，多次调用共享同一个加载好的模型。避免重复加载浪费内存。这里面初始化了 OCR、布局分析、表格识别、公式识别等所有 pipeline 子模型。

第 5 站：pipeline_middle_json_mkcontent.py → union_make()

第 5 课学过的——把中间 JSON 转为 Markdown 或 content_list。这个文件约 1000 行，是所有输出格式的"翻译器"。

第 6 站：data_reader_writer.py → FileBasedDataWriter

写入器——负责把字符串或二进制内容保存到磁盘。之所以抽成抽象层，是为了同时支持本地文件和 S3 云存储。

3. 四个常用修改场景

理解了主干道后，下面四种修改是实际开发中最常见的需求。每种都告诉你"改哪里"和"为什么改那里"。

场景 1：修改默认引擎

需求：想让 mineru 命令默认用 pipeline 而不是 hybrid。

改哪里：mineru/cli/client.py 中 Click option 的 default 参数。

为什么：CLI 参数的默认值在 @click.option 装饰器中定义，引擎选择逻辑本身在 common.py 中——但改默认应该改在参数定义层，而不是调度层。

场景 2：增加新的输出格式

需求：想在 Markdown 和 JSON 之外，额外输出纯文本 TXT 文件。

改哪里：在 mineru/utils/enum_class.py 的 MakeMode 中加一个新值（如 PLAIN_TXT），然后在 pipeline_middle_json_mkcontent.py 的 union_make() 中添加对应的生成逻辑。

为什么：MakeMode 是输出的"开关"，union_make 是输出的"工厂"。新增格式只需要在这两个地方扩展，不影响现有逻辑。

场景 3：调整 OCR 模型的默认语言

需求：默认用 ch_server 而不是 ch。

改哪里：mineru/backend/pipeline/model_init.py 中 OCR 初始化的 lang 默认参数（约第 78 行）。

为什么：model_init 是 pipeline 引擎所有模型的初始化入口，OCR 语言在这里传给 PytorchPaddleOCR 的构造函数。注意 CLI 参数 --lang 的默认值在 client.py 中——两处最好一起改以保证一致性。

场景 4：修改处理窗口大小

需求：显存小的机器想减少每次处理的页数，防止 OOM。

改哪里：mineru/utils/config_reader.py 中的 get_processing_window_size() 函数（默认值 default=64），或者直接设置环境变量 MINERU_PROCESSING_WINDOW_SIZE。该函数在 pipeline_analyze.py、vlm_analyze.py、hybrid_analyze.py 等后端入口处被调用。

为什么：处理窗口机制决定了"一次加载多少页进显存"。窗口越小显存占用越低但总体速度越慢。环境变量是运行时覆盖，改 config_reader.py 里的默认值是永久修改。注意 batch_analyze.py 中控制单批推理大小的是 batch_ratio 与 LAYOUT_BASE_BATCH_SIZE 等常量，与"处理窗口"是两个不同层级的概念。

修改原则

修改前先在 mineru/utils/enum_class.py 和 mineru/utils/config_reader.py 中搜索相关常量或配置。MinerU 把可配置项集中在枚举类和配置文件中，尽量避免硬编码分散在各处。

4. 调试技巧

4.1 开启 DEBUG 日志

# 方法 1：环境变量（推荐）
export MINERU_LOG_LEVEL=DEBUG

# 方法 2：在代码中临时设置
from loguru import logger
logger.remove()
logger.add(sink=..., level="DEBUG")

DEBUG 日志会打印每个处理步骤的输入输出、耗时和异常堆栈。遇到问题时这是第一优先级该做的事。

4.2 在代码中插入断点式日志

当想观察某个变量的中间值时：

from loguru import logger

# 打印变量的类型和内容
logger.debug(f"middle_json keys: {middle_json.keys()}")
logger.debug(f"page 0 has {len(pdf_info[0]['preproc_blocks'])} blocks")

# 打印嵌套结构的摘要
for block in pdf_info[0]['preproc_blocks'][:3]:
    logger.debug(f"  block type={block['type']}, lines={len(block['lines'])}")

4.3 用中间 JSON 隔离问题

如果输出 Markdown 有问题，先保存 middle_json（第 6 课的方法），然后检查是"模型推理错了"还是"middle_json → Markdown 转换错了"。前者看 model_list，后者看 union_make() 的逻辑。

4.4 最小可复现案例

调试时用单页 PDF 而不是 100 页的 PDF。CLI 中指定页码范围：

mineru -p huge_doc.pdf -o debug_output -s 0 -e 0
# 只解析第一页（-s 0 -e 0，从第 0 页到第 0 页）

这条原则适用于所有场景——问题定位从最小单元开始。

5. 代码贡献流程

如果你修复了一个 Bug 或增加了一个功能，以下是提 PR 的标准流程：

# 1. Fork 项目仓库
# 2. Clone 到本地
git clone https://github.com/YOUR_USERNAME/MinerU.git
cd MinerU

# 3. 创建功能分支（命名清晰）
git checkout -b fix/ocr-default-lang    # Bug 修复
git checkout -b feat/add-txt-output     # 新功能

# 4. 修改代码（参考上面四个场景的路径）

# 5. 运行现有测试，确保没搞坏已有的功能
python -m pytest tests/unittest/test_e2e.py -v

# 6. 如果新增功能，写一个最小测试用例
#    放在 tests/unittest/ 下

# 7. 提交（commit message 要说明"改了什么"和"为什么改"）
git commit -m "fix: use ch Server as default OCR model for pipeline

The medium rec model provides better accuracy for Chinese documents,
and the performance difference is negligible on modern hardware."

# 8. Push 并创建 PR
git push origin fix/ocr-default-lang
提交前必查清单

1. 是不是只改了必要的文件？不要顺手重构无关代码。
2. 改动是否兼容现有 API？改了函数签名要确认所有调用方。
3. 测试是否全部通过？新增功能是否有对应的测试？

6. PEP 8 编码规范速查

MinerU 遵循 PEP 8，以下是最高频的规则：

规则示例
缩进 4 空格不用 tab，不改编辑器设置的前提下保持一致
一行不超过 100 字符超长参数列表换行后用 4 空格悬挂缩进
函数/变量用小写下划线doc_analyze_streaming、pdf_bytes_list
类名用大驼峰AtomModelSingleton、FileBasedDataWriter
导入顺序标准库 → 第三方库 → 项目内模块，每组之间空一行
逗号后加空格[1, 2, 3] 而不是 [1,2,3]
字符串用双引号"hello"（和 Python 标准库一致）
文件末尾留一个空行Git 不标记 "No newline at end of file"

7. 小测验

问题 1： 如果要修改 Markdown 输出中公式的分隔符（把 $$ 改成 \[），应该改哪个文件？

  1. CLI 参数的定义文件
  2. pipeline_middle_json_mkcontent.py（输出生成逻辑）
  3. OCR 模型文件
  4. 版本号文件
查看答案

B。输出格式（包括 LaTeX 分隔符）的生成逻辑在 pipeline_middle_json_mkcontent.py 中。具体的分隔符配置在 mineru.json 的 latex-delimiter-config 字段（第 3 课讲过），改配置文件即可无需改源码。

问题 2： 追踪调用链时，mineru 命令的 Python 入口函数在哪个文件？

  1. mineru/cli/client.py 的 main()
  2. mineru/cli/common.py 的 do_parse()
  3. mineru/backend/pipeline/pipeline_analyze.py 的 doc_analyze_streaming()
  4. mineru/version.py
查看答案

A。pyproject.toml 中的 mineru = "mineru.cli.client:main" 定义了 CLI 命令到 Python 函数的映射。main() 是 Click 框架的入口函数，解析参数后调用 common.py 中的 do_parse()。

问题 3： AtomModelSingleton 为什么用单例模式？

  1. 为了代码更好看
  2. 避免重复加载模型——多个文档共享同一个已加载的模型实例，节省内存和加载时间
  3. 因为 Python 不支持多例
  4. 为了绕过 GIL 限制
查看答案

B。模型加载耗时几十秒到几分钟，显存占用几 GB。全局共享一个实例 = 只加载一次、只占一份显存，对批量处理至关重要。

8. 动手挑战

挑战 1：追踪阅读

用 IDE 的"跳转到定义"功能，追踪 mineru/cli/client.py:main() 到底调用了哪些函数。目标是找到 do_parse() 中 _process_pipeline() 的完整调用路径。（提示：从 common.py 开始顺藤摸瓜。）

挑战 2：发现隐藏配置

在 mineru/utils/os_env_config.py 中找出所有可用的 MINERU_* 环境变量。记录下你不知道的那些——它们就是 MinerU 的"隐藏菜单"。

挑战 3：阅读并复述

阅读 mineru/utils/enum_class.py 中的 BlockType 枚举。然后不看文件，默写出至少 10 种块类型及其含义。这是检验你对"块类型"理解程度的最好方式。
