1. 场景引入：单证解析到底在解什么？

回到你的最终目标：从发票、合同、报表中自动提取结构化信息。你可能遇到过这样的业务场景：

  • 财务部每月处理 5000 张发票，需要自动录入系统
  • 法务部想从 1000 份合同中搜索特定条款
  • 运营团队需要把季度报表数据汇总到分析平台

这些场景的共性需求只有一个：把 PDF 里的信息"读懂"并变成机器可处理的格式。

但不同单证的结构差异很大——MinerU 对它们的处理方式也不同。我们先看看三类常见单证的特点。

2. 单证类型速览

🧾

发票

结构固定，有标准字段（发票号、日期、金额、税率、购销方信息）。挑战在于表格嵌套、二维码干扰、印章遮挡文字。

📄

合同

以文字段落为主，有条款编号、页眉页脚。挑战在于多栏排版、跨页表格、法律术语中的特殊字符。

📊

报表

大量表格、图表混排，可能包含脚注。挑战在于表格合并单元格、跨页断表、图表文字提取。

💡 核心思路

没有一种配置能完美解析所有文档。好的做法是先识别文档类型，再选择合适的引擎和参数。后续课程我们会学到如何根据文档特征自动选择配置。

3. 上手实践：解析项目 Demo 文档

MinerU 项目自带了 4 个示例 PDF。我们逐个解析，看看效果。

3.1 准备工作：确认环境

确保你在项目根目录下：

cd /c/Users/zm/eciproject/mineru/MinerU

检查 MinerU 是否已安装：

mineru --help

如果看到帮助信息，说明环境就绪。如果没有，请回顾第 1 课的安装步骤。

3.2 解析第一个文档

我们先用 hybrid-engine（默认引擎）解析 demo1.pdf：

mineru -p demo/pdfs/demo1.pdf -o demo/output/lesson4
📝 注意

首次运行会下载模型文件，需要联网。下载完成后会自动缓存，后续解析不再重复下载。

解析完成后，查看输出目录的内容：

ls demo/output/lesson4/demo1/

你会看到类似这样的文件结构：

demo/output/lesson4/demo1/
├── demo1.md          # 解析结果 Markdown
├── demo1.json        # 解析结果 JSON（如开启）
├── images/           # 提取的图片
│   └── figure-1.jpg
└── metadata.json     # 解析元数据（耗时、页数等）

4. 读懂输出：逐段理解 Markdown 结果

打开 demo1.md，看看 MinerU 输出的内容。我们逐段解读：

文档头

MinerU 是一个开源的高精度文档解析引擎

这是文档正文开始。MinerU 会自动去掉页眉页脚和页码，直接从正文开始输出。

标题层级

# 一级标题 ## 二级标题

MinerU 用 Markdown 的 # 符号表示标题层级。# 越多，标题级别越低。如果文档中的标题层级不对（比如跳级），可能是原始文档的标题样式不规范。

表格

| 列1 | 列2 | 列3 | | --- | --- | --- | | 数据1 | 数据2 | 数据3 |

表格被转为 HTML 格式嵌入 Markdown 中（默认的表格输出格式）。每个单元格的内容被正确分割到对应列。

图片

![图片描述](images/figure-1.jpg)

文档中的图片被提取到 images/ 目录，Markdown 中用相对路径引用。

公式

$$ E = mc^2 $$

数学公式被转为 LaTeX 格式，用 $$ 包裹（行间公式）或 $ 包裹（行内公式）。

✅ 输出看起来不错？

如果内容正确、结构清晰，说明文档不复杂，MinerU 开箱即用。如果有一些问题，别担心——下一节我们专门讲排查方法。

5. 实践：对比三种引擎的解析效果

MinerU 的三个引擎在不同文档上表现各异。我们来做个实验——用同一份文档，分别用三个引擎解析，对比效果。

# 用 pipeline 引擎
mineru -p demo/pdfs/demo2.pdf -o demo/output/demo2-pipeline -b pipeline

# 用 hybrid-engine（默认，不指定也行）
mineru -p demo/pdfs/demo2.pdf -o demo/output/demo2-hybrid

# 用 vlm-engine（需要 GPU）
mineru -p demo/pdfs/demo2.pdf -o demo/output/demo2-vlm -b vlm-engine

你应该关注什么？

对比维度怎么看
文字完整度是否有漏字、错字、乱码？扫描件 OCR 识别是否准确？
布局保真度段落的先后顺序是否正确？多栏文档的阅读顺序是否对？
表格识别表格结构是否完整？单元格内容是否对号入座？
处理速度对比三个引擎各自花了多长时间？
💡 引擎选择经验
文档类型推荐引擎原因
文本型 PDF（Word/LaTeX 导出）hybrid-engine速度快，精度已足够
扫描型 PDFpipeline 或 hybrid内置 OCR，效果稳定
复杂排版的扫描件vlm-engine（有 GPU 时）VLM 理解能力强
纯文字快速提取pipeline资源占用最低，适合批量处理

6. 常见问题排查

实际解析中，你可能会遇到这些问题。以下是常见场景和解决方案：

问题 1：输出有乱码 / 文字缺失

可能原因解决方法
PDF 含嵌入字体但提取失败换 hybrid-engine 或启用 OCR 方式：-m ocr
文档是扫描件但用了文本模式用 -m ocr 强制 OCR
语言不在默认识别范围检查文档语言，配置 lang 参数

问题 2：表格歪了 / 单元格合并错乱

可能原因解决方法
表格布局复杂（合并单元格、无边框表）尝试 vlm-engine（如果有 GPU）
表格跨页被截断MinerU 的 hybrid-engine 能处理跨页表格
表格中没有明显边框线hybrid-engine 比纯 pipeline 效果更好

问题 3：阅读顺序错乱

可能原因解决方法
多栏排版（如报纸风格）hybrid-engine 自动处理多栏顺序
页面中有浮动物体（文本框、图片）检查原始 PDF 中这些元素的排列方式
PDF 生成工具导出了不规范的内部结构尝试转换为图片后再解析

问题 4：速度太慢

原因优化方法
文档页数太多分批处理，或者用 -s（起始页）和 -e（结束页） 指定页码范围
pipeline 使用了 CPU 模式如果 GPU 可用，确认是否正确配置了 GPU 加速
启用了不需要的功能（如公式检测）关闭无关功能：-f false

7. 实用技巧

7.1 只处理特定页码范围

mineru -p demo.pdf -o output -s 0 -e 4

这在调试时非常有用——先只解析前几页看看效果，确认配置正确后再全量处理。

注意：页码从 0 开始计数。例如 -s 0 -e 4 表示解析第 0 到第 4 页（共 5 页）。

7.2 强制使用 OCR 模式

mineru -p demo.pdf -o output -m ocr

当文档虽然是文本型 PDF 但提取文字效果不好时（比如字体特殊、含大量生僻字），强制 OCR 可能更好。

7.3 同时输出 Markdown 和 JSON

mineru -p demo.pdf -o output

Markdown 给人看，JSON 给程序用。JSON 包含更丰富的元数据（每个元素的位置、类型、置信度等）。

8. 小测验

问题 1： 扫描型 PDF 解析效果不好，你应该优先尝试什么？

  1. 换一个 PDF 查看器
  2. 用 -m ocr 强制 OCR
  3. 把 PDF 转成 Word
  4. 降低图像分辨率
查看答案

B。扫描型 PDF 本质上是图片，没有内嵌文字。强制 OCR 模式会调用光学字符识别引擎从图片中提取文字。

问题 2： 你有一份复杂的多栏文档，主要挑战是什么？

  1. OCR 无法识别
  2. 文字大小不一致
  3. 阅读顺序可能错乱（左右栏串读）
  4. 文件太大无法处理
查看答案

C。多栏文档的最大挑战是阅读顺序。如果解析引擎不能正确理解两栏之间的先后关系，输出会变成左右栏交叉混排。

问题 3： 批量处理大量 PDF 时，想先看看前 3 页的效果再决定配置，应该用什么参数？

  1. --max_pages 3
  2. -s 0 -e 2
  3. --preview
  4. --dry_run
查看答案

B。-s 0 -e 2 指定只解析前 3 页（从第 0 页开始到第 2 页，共 3 页），确认效果后再去掉这个参数全量运行。注意页码从 0 开始计数。
