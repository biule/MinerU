1. 问题现场：一张 210×18 小图，Pipeline 返回空

测试素材是一张 4 个字的小图 output-onlinepngtools.png，尺寸 210×18 像素。用第 6 课学的 pipeline do_parse 调 parse_method="ocr" + p_lang_list=["ch"] 去解析，输出 middle.json 长这样：

{ "pdf_info": [{ "preproc_blocks": [], "page_idx": 0, "page_size": [1343, 115], "discarded_blocks": [], "para_blocks": [] }], "_backend": "pipeline", "_version_name": "3.4.4" }

preproc_blocks、para_blocks 全部为空 —— 连一个文字块都没检出。但人眼看图，上面明明有 4 个清晰的汉字。

关键认知

这不是 OCR 失败，是 Layout 模型 在 OCR 之前就判了"此图无文字"。OCR-det / OCR-rec 根本未被调用。

2. 根因分析：Pipeline 的三段式架构与小图矛盾

Pipeline 后端对每张图的处理顺序是：

graph LR A[原始图片] --> B["① Layout
(PP-DocLayoutV2)"] B --> C["② OCR-det
(PaddleOCR small det)"] C --> D["③ OCR-rec
(PaddleOCR small/medium rec)"] D --> E["④ 后处理
(排序/合并/输出)"] style B fill:#fee2e2,stroke:#ef4444 style C fill:#d1fae5,stroke:#10b981 style D fill:#dbeafe,stroke:#3b82f6

① Layout（PP-DocLayoutV2） 是第一个也是唯一一个判断"有没有文字"的关卡。这个模型训练数据几乎全是 A4 比例（≈ 0.707）的文档页面。当输入是一张 7467×640（长宽比 ≈ 11.7）的横向长窄图时，模型把它当成了"页面边缘空白区"——直接返回 0 个块。

② 的 OCR-det 检测模型（ch_PP-OCRv6_small_det_infer）对输入尺寸也有约束：默认短边限制 320px。原图短边只有 18px，即使不做 Layout 直接喂给 det，也会因为太小而检不到文字框。这就是为什么第 6 课测试里要把短边放大到 640 再喂。

组件输入要求210×18 原图放大到 640 短边后
PP-DocLayoutV2 接近 A4 比例（≈0.707） 判空：长宽比 11.7 完全在分布外 仍然判空：长宽比未变
PaddleOCR det 短边 ≥ 320px 短边 18px → 检不到框 短边 640px → 正常检测
PaddleOCR rec 裁出的单字图 ≥ 32px 高 det 没裁出字，不会走到这 置信度 0.998
结论

对这种小图，Layout 模型是唯一瓶颈。OCR-det 和 OCR-rec 本身完全能识别——前提是绕开 Layout、直接把放大后的图喂给 PaddleOCR。

3. 绕开 Layout：PaddleOCR 直调

MiniU 内部已经封装了 PytorchPaddleOCR（位于 mineru/model/ocr/pytorch_paddle.py），提供三个接口：

调用方式行为适用场景
ocr(img, det=True, rec=True)检测 + 识别，完整走一遍通用 OCR
ocr(img, det=True, rec=False)只检测文字框位置只需要坐标
ocr(img, det=False, rec=True)只识别（需预先裁好单字）已知位置的文字

返回值结构：[[[box, (text, score)], ...]]

[[ [[[x1,y1],[x2,y2],[x3,y3],[x4,y4]], ("进料对口", 0.998)] ]]

核心代码（完整版见 tests/unittest/test_imgbase64.py 中的 test_paddleocr_raw_baseline）：

from mineru.model.ocr.pytorch_paddle import PytorchPaddleOCR import numpy as np from PIL import Image from io import BytesIO # 1. base64 解码 + 短边放大到 320 raw = base64.b64decode(b64_str) im = Image.open(BytesIO(raw)).convert("RGB") scale = 320 / min(im.size) if scale > 1: im = im.resize((int(im.width*scale), int(im.height*scale)), Image.LANCZOS) # 2. PIL(RGB) -> numpy(BGR) arr = np.array(im)[:, :, ::-1].copy() # 3. 初始化 + OCR（模型仅首次加载，后续复用） ocr = PytorchPaddleOCR(lang="ch") # "ch" = small rec，够用且快 results = ocr.ocr(arr, det=True, rec=True) # 4. 提取文字 for box, (text, score) in results[0]: print(f"{text} ({score:.3f})")

4. Model 体系速览

PytorchPaddleOCR(lang="ch") 到底加载了哪几个模型？查 models_config.yml：

langdet（检测）rec（识别）速度精度
chch_PP-OCRv6_small_detch_PP-OCRv6_small_rec快够用（简单字）
ch_serverch_PP-OCRv6_small_detch_PP-OCRv6_medium_rec慢 30-40%略高
ench_PP-OCRv6_small_deten_PP-OCRv5_rec快英文专优
korean / arabic / …ch_PP-OCRv6_small_det各自语种的 rec——
关键发现：无论选哪个 lang，det 模型完全相同（都是 small_det）。ch vs ch_server 差别只在 rec。
对于清晰小图（如"进料对口"），small rec 置信度已达 0.998，medium rec 纯粹浪费计算。

模型文件物理路径（以 ModelScope 为例）：

~/.cache/modelscope/models/ OpenDataLab--PDF-Extract-Kit-1.0/ ← pipeline 全家桶（~500MB） snapshots/master/models/ Layout/PP-DocLayoutV2/ ← Layout 模型（/image_ocr 不用） OCR/paddleocr_torch/ ch_PP-OCRv6_small_det_infer.safetensors ← det ch_PP-OCRv6_small_rec_infer.safetensors ← rec (ch) ch_PP-OCRv6_medium_rec_infer.safetensors ← rec (ch_server) TabRec/ ← 表格模型（/image_ocr 不用） TabCls/ ← 表格分类（/image_ocr 不用） MFR/ ← 公式识别（/image_ocr 不用）

生产环境如果只跑 OCR，可以只保留 OCR/ 目录下的 det + 你选的 rec 两个文件（~20 MB），其他全删。

5.2 端点 1：POST /image_ocr/json

接收 JSON body，批量处理多张图。每张图独立解码、独立跑 OCR，并发执行。

POST /image_ocr/json

Content-Type: application/json

# 请求 curl -X POST http://127.0.0.1:8000/image_ocr/json \ -H "Content-Type: application/json" \ -d '{ "images": { "tag1": "data:image/png;base64,iVBORw0KGgo...", "tag2": "/9j/4AAQSkZJRgABAQAAAQABAAD..." }, "lang": "ch" }' # 响应 { "results": { "tag1": { "texts": ["进料对口"], "boxes": [[[100,20],[300,20],[300,80],[100,80]]], "scores": [0.998] }, "tag2": { "error": "image_base64 length is 1 mod 4: likely truncated", "texts": [], "boxes": [], "scores": [] } }, "lang": "ch", "version": "3.4.4" }

容错设计：某张图 base64 解码失败时，results[key] 中多一个 error 字段，其余图正常返回。不会因为一张图炸了整个请求。

5.3 端点 2：POST /image_ocr/upload

接收 multipart/form-data，单张图上传。适合 Swagger 页面点 Try it out 手动测试。

POST /image_ocr/upload

Content-Type: multipart/form-data

# 请求 curl -X POST http://127.0.0.1:8000/image_ocr/upload \ -F "file=@output-onlinepngtools.png" \ -F "lang=ch" # 响应 { "texts": ["进料对口"], "boxes": [[[100,20],[300,20],[300,80],[100,80]]], "scores": [0.998], "lang": "ch", "version": "3.4.4" }

5.4 三条共享函数

函数职责关键细节
_decode_b64_payload(value) 安全的 base64 解码 自动剥 data:image/png;base64, 前缀
自动补全末尾 = / == padding
长度 mod 4 = 1 时明确报错"复制时截断"
_preprocess_image_bytes(raw, min_side=320) 图片预处理 EXIF 自动转正
RGBA/LA/P → 白底 RGB
短边 <320 → LANCZOS 等比放大
_ocr_one(raw_bytes, lang) 单张图 OCR 内核 调预处理 → 调 OCR → 格式化返回 {texts, boxes, scores}
两张端点共用这一份逻辑

5.5 OCR 引擎单例缓存

_get_image_ocr_engine(lang) 用线程锁 + 全局变量缓存 PytorchPaddleOCR 实例。同 lang 的后续请求不再重新加载模型，只重建预处理和推理：

_image_ocr_singleton: Optional["object"] = None _image_ocr_singleton_lock = threading.Lock() def _get_image_ocr_engine(lang: str): global _image_ocr_singleton with _image_ocr_singleton_lock: cache = _image_ocr_singleton if cache is not None and getattr(cache, "_mineru_lang", None) == lang: return cache # ← 命中缓存，跳过 5s 的模型加载 engine = PytorchPaddleOCR(lang=lang) engine._mineru_lang = lang _image_ocr_singleton = engine return engine

9. 小结

三个核心收获

1. Pipeline 对小图"识别空白"的根因是 Layout 判空，不是 OCR 失败。OCR-det + rec 本身对放大后的图完全能工作。
2. 绕过 Layout 的正确方式：PytorchPaddleOCR(lang="ch").ocr(img, det=True, rec=True)，跳过整个 Layout → OCR 流水线，直接做检测+识别。
3. 生产 API 设计：/image_ocr/json 批量 key-value 并发处理，/image_ocr/upload 单文件方便测试，共享 _ocr_one 内核，OCR 引擎单例缓存避免重复加载。
